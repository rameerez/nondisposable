# Plan: lookalike precision, multi-source blocklists, and a fresh-domains list

Status: v2, revised after codex adversarial review (docs/plans/2026-10-17-codex-plan-review.md). §6 overrides earlier sections where they conflict.
Owner: Javi R (rameerez). Trigger: abusive signups at a production app using this gem, 2026-10-16/17.

## 0. Why

Two failures surfaced in one incident:

1. **Blocklist lag.** Attackers signed up with `@mail-burn.com`, a live public
   10-minute inbox. The gem pulls only `disposable-email-domains/disposable-email-domains`
   (9,895 domains), which does not list it. Three other maintained lists already did:
   `disposable/disposable-email-domains`, `groundcat/disposable-email-domain-list`,
   `amieiro/disposable-email-domains`.
2. **The lookalike rule is not safe to turn on.** `reject_lookalike_domains`
   (OSA distance ≤ 1 against `data/email_providers.txt`) was replayed against the
   Tranco top 1M (list fetched 2026-10-17). It flags **707** domains
   (`docs/evidence/2026-10-17-tranco-top1m-lookalike-hits.csv`: rank, domain,
   suggestion). Many are real typos/typosquats (`gmial.com`, `gamil.com`,
   `hotmial.com`), but many are large real organisations whose staff would be
   refused with "did you mean …?":
   - `ge.com`, `ml.com`, `mi.com`, `se.com`, `de.com`, `te.com`, `ae.com` → `me.com`
   - `ea.com`, `aa.com`, `ca.com`, `ba.com` → `ya.com`
   - `bol.com`, `aon.com`, `uol.com` (a major Brazilian mail provider) → `aol.com`
   - `one.com` → `ono.com`; `hive.com`, `life.com`, `jive.com`, `mlive.com` → `live.com`
   - `grail.com`, `pmail.com`, `qmail.com`, `cmail.com` → `gmail.com`

   Against one production app's signups (66 distinct email domains) it flags only 6, and all
   6 are real typos (`gmailmcom`, `gmail.con`, `outlook.ed`, `gmai.com`, `gmal.com`,
   `jmail.com`). So the rule happens to work on one small app's data and is unsafe
   in general. Top suggestion targets among the 698: `me.com` 47, `rr.com` 35,
   `ya.com` 28, `usa.com` 27, `gmail.com` 25, `aol.com` 25, `qq.com` 23,
   `msn.com` 23, `mac.com` 23, `bk.ru` 23. Short provider names dominate.

Guiding constraint (from the gem's own docs and the host app): **a false positive is
a real person who cannot sign up. Precision over recall, everywhere.**

## 1. Workstream A: lookalike precision (blocks enabling `reject_lookalike_domains`)

### A1. Labelled corpus (the test oracle, built first)

- Take the 698 Tranco hits plus the 6 CarHey typos plus the known typos in the
  gem's current tests. Label each `typo` (a typosquat / parked / for-sale / mail-catcher
  domain nobody legitimately uses as their own address) or `real` (an organisation
  or service people legitimately have addresses at).
- Evidence per domain, captured to `test/fixtures/lookalike_corpus.csv` with
  columns `domain,suggestion,label,evidence` (evidence = short reason: homepage
  title, "parked", "for sale", "redirects to gmail.com", "no MX", Wikipedia/org name).
- Labelling: an automated pass collects the evidence (HTTP title + final URL, MX
  records). A model proposes labels; a human (owner) spot-checks every `real`
  verdict on a short provider and every disagreement. **Ambiguous → `real`**
  (precision bias).
- The corpus is frozen into the test suite. CI fails if any `real` row is flagged.
  Recall on `typo` rows is reported, not asserted at 100%.

### A2. Algorithm changes (candidate set; codex to attack)

Applied in order; each is a reason to NOT flag.

1. **Exact protected match.** Keep `email_providers.txt` exact-match exemption.
2. **Bundled `known_real_domains.txt`.** Every `real` row from the corpus, plus a
   generated set: domains in the Tranco top N (N to be measured: 100k?) that are
   one edit from a provider AND are not labelled `typo`. Exact match → never flagged.
   Regenerated by a rake task; documented as a list, never hand-edited without evidence.
3. **Short-label guard.** If the provider's registrable label is ≤ 3 chars
   (`me`, `ya`, `qq`, `rr`, `bk`, `aol`, `msn`, `mac`, `att`, `sky`, `ono`, `wp`,
   `hey`, `gmx`, `usa`…), only TLD-side edits are allowed (`me.cmo`, `aol.con`,
   `qq.co`), never label edits. Label edits on a 2–3 letter name collide with
   real organisations at an unacceptable rate (evidence: §0).
4. **Typo model for label edits** on longer labels (≥ 4 chars). Allowed:
   adjacent transposition (`gmial`), deletion (`gmal`, `hotmal`), doubled-letter
   insertion (`gmmail`), substitution or insertion of a key **adjacent on QWERTY**
   (`gnail`, `gmsil`, `hotnail`). Disallowed: substitution by a non-adjacent
   key (`grail`, `pmail`, `qmail`, `cmail`, `jive`, `hive`), insertion of a
   non-adjacent letter (`mlive`, `alive`). AZERTY/QWERTZ: decide whether to union
   adjacency maps (Spain/LatAm use QWERTY; FR AZERTY; DE QWERTZ).
5. **TLD-side edits stay permissive** (`gmail.con`, `gmail.co`, `outlook.ed`,
   `gmailmcom`): these are the measured high-precision cases.

Open question for review: is (4) over-engineered vs (2)+(3) alone? Measure all
combinations on the corpus; pick the simplest that has zero `real` hits and best
`typo` recall.

### A3. API / compatibility

- Behaviour change only when `reject_lookalike_domains = true` (default false), and
  `Nondisposable.suggestion_for` gets more conservative. Minor version bump (0.5.0),
  CHANGELOG entry naming the false positives found.
- `config.lookalike_distance` keeps meaning OSA distance; values > 1 documented as
  unsafe.

### B2. Design

- `config.sources`: an ordered list of source descriptors
  `{name:, url:, format: :lines|:json, trust: :primary|:corroborating}`.
  Default stays `[disposable-email-domains]` alone (no behaviour change for existing
  hosts). A documented preset `Nondisposable::Sources::RECOMMENDED`.
- **Merge rule:** a domain is blocked if it is in any `primary` source, OR in
  ≥ `config.corroboration_threshold` (default 2) `corroborating` sources.
- **Always-applied allowlist** (`data/never_disposable.txt`, bundled + host
  `excluded_domains`): the 260 known-real set, plus major ISPs. Wins over every source.
- **Privacy aliases are a policy, not a bug:** `config.block_privacy_relays`
  (default false). `duck.com`, `simplelogin.com`, `addy.io`, `passmail.com`,
  `privaterelay.appleid.com` are allowed unless the host opts in.
- **Safety rails in the updater:** per-source fetch timeout + size ceiling; a
  source whose count drops > 50% or grows > 3× vs the last run is skipped (keep
  last good), logged; a failed source never empties the table (current behaviour:
  one source, all-or-nothing replace); store `source` provenance per row
  (new column, migration generator) so `disposable?` can explain itself and a bad
  source can be purged.
- Licence: only ingest sources with a permissive licence; `amieiro` excluded
  (no licence and 28 FPs).

## 3. Workstream C: an open-source "fresh disposable domains" list (separate repo)

Goal: catch new burner domains in days, not weeks, with **evidence attached to every
entry**, so other lists (and upstream PRs) can trust it.

- Repo (name TBD by owner, e.g. `rameerez/fresh-disposable-domains`), CC0 data, MIT code.
- Daily GitHub Action:
  1. **Discover**: visit a curated registry of public temp-mail generator sites
     (`generators.yml`: URL + how to read the generated address: DOM selector or
     JSON API). Headless Chromium; record every domain offered. Also diff the other
     public lists (domains newly added anywhere).
  2. **Verify** each candidate: resolves MX; not in the never-disposable allowlist;
     not in Tranco top-10k; not a known privacy relay. Optionally confirm deliverability
     by generating an address and checking the inbox UI receives a probe (later).
  3. **Record evidence**: `evidence/<domain>.json` (first_seen, generator URL,
     screenshot path, MX hosts, sources that also list it), screenshot PNG.
  4. **Publish**: `domains.txt` (one per line), `domains.json` (with first_seen +
     evidence URL), and a changelog. Entries never silently removed: removals need
     a PR with a reason (false-positive process).
- Automated checks in CI: format, no allowlisted domain, no PSL public suffix,
  every entry has evidence, list size sanity bounds.
- Feeds back: the gem can consume it as a `primary` source once it has a track record;
  evidence screenshots make upstream PRs to `disposable-email-domains` trivial.
- Ethics/ToS: only read pages a normal visitor sees; low rate; honour robots.txt;
  no account creation; no CAPTCHA solving.

## 4. Order of work

1. A1 corpus + A2 algorithm + tests → gem 0.5.0 (unblocks CarHey enabling lookalike).
2. B multi-source + allowlist + provenance → 0.6.0.
3. C new repo, scaffold + discovery for a first handful of generators; publish only
   after owner approves the name and the first evidence batch.

Each step: codex adversarial review of the code, one round, owner triages.

## 5. Questions for the reviewer

- Does the short-label guard + typo model still miss a class of false positive the
  Tranco corpus cannot show (e.g. corporate domains outside the top 1M, IDNs,
  country second-levels like `co.uk` / `com.br` / `com.es`)?
- Is "ambiguous → real" labelling enough to keep the oracle honest?
- Multi-source: is ≥ 2 corroborating sources the right default, given that many lists
  copy each other (corroboration may be illusory)?
- Updater: is a provenance column worth a migration for existing hosts?
- Anything in workstream C that is legally or operationally risky?

## 6. Decisions after adversarial review (v2, these override §1–§3)

Codex review: `docs/plans/2026-10-17-codex-plan-review.md` (18 findings). Triage by
the session lead; owner can overrule any line.

Reproducibility: Tranco top-1M CSV downloaded 2026-10-17 from
`https://tranco-list.eu/top-1m.csv.zip` (file dated 2026-10-16, sha256 prefix
`a166c559bdf76fce`); scan script `docs/evidence/tranco_lookalike_scan.rb`;
707 unique hits (the 698 in §0 was a partial count, finding 7).

**A. Lookalike: hard reject only what we KNOW is a typo; everything else is confirmable.**
(findings 1–4, 6)
- Offline we cannot tell `ge.com` from `gmial.com` with certainty, so no rule
  derived from a corpus may hard-reject an unseen domain.
- New mode `config.reject_lookalike_domains = :confirmable` (keep `false` default,
  keep `true` meaning "reject" for backward compatibility, but its behaviour becomes
  the safe one below):
  1. **Hard reject** when the domain is in bundled `data/known_typo_domains.txt`
     (reviewed `typo` labels with evidence) or is an invalid-TLD typo (already
     shipped).
  2. **Confirmable** for any other lookalike: the validator adds the suggestion
     error unless the record carries a confirmation (virtual attribute set by the
     host's "Sí, es correcto" checkbox/resubmit; gem ships a small concern
     `Nondisposable::ConfirmableEmail` + docs). A real `ge.com` user resubmits once,
     never locked out.
  3. Typo model (short-label guard, adjacency) is used only to RANK/limit what
     becomes a suggestion, never to justify a hard reject.
  4. Valid alternative suffixes (`yahoo.com.au` vs `.ar`, `web.dev` vs `web.de`) are
     never hard-rejected (they are real domains) → at most confirmable.
- Evaluation (finding 1): corpus split into a labelled set and an untouched
  holdout BEFORE tuning; report precision/recall of the suggestion ranker on the
  holdout; the hard-reject list is evaluated only for provenance (every row has
  evidence), not used as its own test oracle.
- Labels (finding 2): website appearance is evidence, not proof. Both directions
  reviewed. Only entries labelled `typo` with strong evidence (typosquat/parking of a
  provider's misspelling, redirect to the provider, registered by a known
  typosquatter, no mailbox service) enter `known_typo_domains.txt`. Uncertain →
  not listed (stays confirmable).
- Canonicalization (finding 6): one `Nondisposable::Domain.normalize` used by
  config, ingestion, `disposable?`, TLD and suggestion paths: strip, downcase,
  trailing dot, IDNA to ASCII (punycode) for matching, never touch the local part.
- CarHey enables `:confirmable` with a UI checkbox after 0.5.0.

**B. Multi-source (findings 5, 8–14): accepted in full, simplified where possible.**
- PSL validation on every ingestion path and on `additional_domains`: reject public
  suffixes (bundle a PSL snapshot; no runtime network).
- Sources declare lineage (`derived_from:`). Corroboration counts distinct ORIGINS
  (`disposable/disposable` imports mailchecker/fakefilter/wesbos → it does not add a
  vote for entries those already carry).
- Precedence table (one place, enforced in validation and seeding):
  `excluded_domains` (host) > bundled `never_disposable.txt` (real providers, ISPs)
  > `additional_domains` (host) > relay policy (`block_privacy_relays`, relays live
  in their own list, NOT in never_disposable) > merged sources.
  Today `additional_domains` is checked BEFORE `excluded_domains` (a host
  exclusion cannot override a host addition). The table above makes host
  exclusions win; document it in README + CHANGELOG and test every row.
- Snapshots: new table `nondisposable_source_snapshots` (source, fetched_at,
  sha256, domain_count, status, domains text) via an ADDITIVE upgrade migration
  generator; the merged `disposable_domains` table is rebuilt from the last good
  snapshot of each source inside one transaction, under an advisory lock
  (serialized publish + seed). Hosts without the new table keep today's
  single-source behaviour (rolling deploy safe).
- Guards: canonical-unique count; streamed byte cap + total deadline; additions
  and removals diffed and logged; a never_disposable domain appearing in any source
  is dropped and logged as a poison signal; first run with all primaries failed →
  keep seed, never publish empty.
- Excluded source: amieiro (no licence, 28 FPs).

**C. Fresh-domains repo (findings 15–17): quarantine-first; design + scaffold only.**
- Discoveries land in `quarantine/`, never in `domains.txt`, until a proof of
  inbox capability exists: a probe mail from a mailbox WE control arrives in the
  generator's UI for that domain (recorded with run ID + artifact hashes).
- Evidence bound to run IDs and sha256 of artifacts; entries re-validated every 30
  days; withdrawal path documented; budgets (max candidates/run, runtime, storage).
- Legal: per-generator ToS review recorded in `generators.yml`; screenshots crop to
  the address widget (no inbox contents); upstream lists are NOT re-licensed, only
  our own observations are CC0; attribution kept.
- Not published until the owner approves the name and the first evidence batch.

Order unchanged: A → B → C. Each implementation gets one codex code review round;
the session lead triages; owner decides releases.
